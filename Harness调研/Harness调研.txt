调研 Coding Agent 的 **harness**，核心不是看它“能不能生成代码”，而是看：

> **它能否把不可靠的模型输出，变成可控、可验证、可恢复、可审计的软件工程过程。**

可以将 harness 理解为模型之外的“控制平面”：负责上下文组装、工具调用、命令执行、状态管理、预算控制、测试验证和失败恢复。

## 一、优先关注的 8 个方面

| 方面 | 重点调研问题 | 关键指标/证据 |
|---|---|---|
| **1. 主循环与任务状态机** | 是简单的 `生成→执行→重试`，还是有明确的 plan/code/review/test/done/failed 状态？停止条件是什么？如何防止死循环和无效重试？ | 状态转换是否清晰；最大步数；重复错误检测；人工接管条件 |
| **2. 上下文工程** | 如何发现相关文件？如何检索代码、裁剪上下文、压缩历史？测试失败信息如何反馈？长任务如何避免上下文污染？ | 有效上下文比例；token 消耗；检索命中率；是否支持符号/调用图/影响面分析 |
| **3. 工具与执行环境** | 支持哪些工具：读文件、补丁、shell、测试、浏览器、MCP？命令是否有超时、输出截断、工作目录约束？补丁是否原子化？ | 工具成功率；超时率；输出丢失率；异常退出处理；跨平台能力 |
| **4. 验证闭环** | 如何判断任务真的完成？是否实际运行测试、lint、类型检查？会不会仅凭模型一句“已完成”就结束？失败测试如何选择和重跑？ | fail-to-pass 率；回归率；验证覆盖率；虚假成功数；最终工作区 diff |
| **5. 状态持久化与恢复** | 进程崩溃、模型超时、机器重启后能否恢复？checkpoint 保存什么？重试会不会重复提交、覆盖用户改动或污染暂存区？ | resume 成功率；幂等性；checkpoint 一致性；并发锁；失败现场保留 |
| **6. 安全与权限边界** | 是否沙箱隔离？能否访问网络、密钥和宿主机文件？如何防仓库 README、网页、工具输出中的提示注入？危险命令是否需审批？ | 文件系统边界；最小权限；secret 脱敏；网络策略；命令审计；注入测试 |
| **7. 成本与运行效率** | 每个成功任务消耗多少 token、时间和工具调用？是否有缓存、增量测试、并行执行和模型路由？ | **成功率@成本**；P50/P95 时延；token/task；测试耗时；缓存命中率 |
| **8. 可观测性与可诊断性** | 能否还原模型看到了什么、调用了什么、为什么重试、为什么结束？日志是文本堆叠还是结构化事件？ | 完整 trace；prompt/config/model 版本；事件时间线；错误分类；任务回放能力 |

## 二、容易被忽略但很重要的方面

### 1. 工作区与变更管理

重点检查：

- 是否使用独立 worktree/容器，避免任务间互相污染。
- 是否保护用户已有修改和 untracked 文件。
- 是否记录真实写入文件，而不只依赖 Git diff。
- commit、rollback、retry 是否幂等。
- 最终 diff 是否超出任务授权范围。
- 空变更、部分成功、测试通过后提交失败等边界如何处理。

很多 harness 的问题不是模型能力不足，而是 **Git 状态、文件写入和重试语义不一致**。

### 2. 失败分类与升级策略

不要只看“是否重试”，还要看它能否区分：

- 模型输出格式错误；
- 工具调用失败；
- 测试失败；
- 环境依赖问题；
- 超时；
- 预算耗尽；
- 需求不明确；
- 权限或安全拒绝。

不同失败应该走不同路径。对所有错误统一“再试一次”，通常只会增加成本。

### 3. 可替换性与工程可维护性

检查：

- 模型 provider 是否可替换；
- agent、executor、validator、state store 是否解耦；
- 配置是否版本化并有 schema 校验；
- 是否能关闭检索、审查、自动重试等模块做消融实验；
- 测试是否覆盖状态机和异常路径，而不只是 happy path。

## 三、调研时必须区分两种 harness

1. **运行 harness**：真正驱动 Agent 完成任务的系统。
2. **评测 harness**：构造任务、运行 Agent、判定结果、统计指标的系统。

一个框架 benchmark 分数高，可能来自运行 harness，也可能来自评测方式。需要检查：

- 是否固定模型、温度、预算和任务集；
- 是否多次运行并报告方差；
- 是否区分模型能力与 harness 能力；
- 是否存在测试泄漏或训练数据污染；
- pass 判定是否运行真实测试；
- 是否统计部分成功、回归和人工介入；
- 是否公开失败案例，而不只展示成功案例。

## 四、建议采用的评价指标

不要只比较单次任务通过率，至少使用下面这组指标：

- **Task success rate**：最终验收通过率。
- **Verified success rate**：经过独立测试验证的成功率。
- **Regression rate**：通过目标测试但破坏既有功能的比例。
- **Success@Cost**：固定 token/金额预算下的成功率。
- **Time to success**：P50/P95 完成时间。
- **Recovery rate**：超时、崩溃或工具失败后的恢复率。
- **Human intervention rate**：需要人工接管的任 务比例。
- **Unsafe action rate**：越权写文件、危险命令、密钥暴露等事件数。
- **Flakiness**：同一任务多次运行的结果波动。

## 五、实际调研方法

建议按以下顺序，而不是先读宣传文档：

1. **画架构图**：模型、控制器、工具、执行环境、状态存储、验证器之间的边界。
2. **跟踪一次完整任务**：从任务输入到最终 diff，记录状态转换和每次工具调用。
3. **注入故障**：模型超时、命令超时、测试失败、进程重启、磁盘错误、空 diff。
4. **做安全测试**：恶意 README、越权路径、危险 shell、secret 文件、网络访问。
5. **跑固定任务集**：简单修改、跨文件重构、隐式需求、长任务、不可完成任务。
6. **做消融实验**：分别关闭检索、review、自动重试、checkpoint，观察成功率和成本变化。
7. **检查失败案例**：判断问题来自模型、上下文、执行器、验证器还是状态管理。
